Enforcement internals Why blackjack?

ENFORCEMENT INTERNALS

The full path from "user taps TikTok" to "Sonder shows a card table" — and back.

The detection → gate flow

1. Target app launches; its window appears
2. SonderAccessibilityService receives TYPE_WINDOW_STATE_CHANGED
   (filtered: targets only, self/system/notification sources ignored,
   debounced against event floods)
3. EnforcementCoordinator queries EnforcementRepository:
   is this package enabled AND not currently granted?
4. If blocked: BlockOverlay raises a full-screen SYSTEM_ALERT_WINDOW
   instantly (covers the target's first frame)
5. BlockActivity (the blackjack gate) starts on top
6. Hand played → result settles into AccessPolicy
   · win at zero debt → grant written (endAt = now + 5 min)
   · loss             → debt += 10 min (cap 60) or lockout written
7. Overlay drops; gate stays until closed or access granted
8. Accessibility events keep refreshing lastSeenMillis while the
   granted app is foreground — a gap >60 s revokes the grant

Why the overlay layer exists

Starting an activity from the background is restricted on modern Android, and even a fast Activity launch shows a frame or two of the target app first. The overlay is drawn the instant the blocked window is detected — before the target's content is meaningfully visible — and the gate activity replaces it. If the overlay permission is missing, Sonder degrades gracefully to the gate activity alone.

The 10-second permission audit

Accessibility can be "on" in Settings yet not yet connected when an app cold-starts — a well-known Android quirk. Sonder schedules its audit 10 seconds after launch, not at launch: by then the service binding has settled, so the check reflects reality. Missing pieces raise a pixel-styled popup with deep links straight into each Settings page, and the audit re-runs when you return from Settings.

Why absolute epoch millis

Every timer — grant end, lockout end, debt, last-seen — is stored as an absolute instant, never a countdown. Consequences:

  • Force-kill Sonder mid-hand? Timers keep running.
  • Reboot? BootReceiver reschedules expiry alarms from the same instants.
  • Doze? AlarmManager with setExactAndAllowWhileIdle still fires.

Known limitations

  • Whole-app granularity — no per-feature (e.g. Shorts-only) gating in v2.
  • Absence detection is event-driven: it notices when the app's window stops appearing, not literally every second.
  • Aggressive OEM battery managers can suspend the service — survival guide.
  • Release APKs fall back to the Android debug key until signing secrets are added — sideloadable, but not Play-publishable.
